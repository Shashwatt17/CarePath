# Secure document vault — Phase 3

The `vault` module is implemented. It stores original documents, user-entered metadata and tags;
it does not extract text, classify medically, run OCR, or create observations. Every new record is
`UPLOADED`. The five processing states remain compatible with later phases.

## Boundaries and persistence

`DocumentController` accepts explicit validated DTOs, `DocumentService` obtains identity through
`Ownership`, and `DocumentRepository` uses parameterized JDBC inside Spring transactions. This
matches the existing session/audit persistence approach. `MedicalDocument` is an internal record,
not a serialized JPA entity. All user queries carry the authenticated owner, including search and
row locks; absent and foreign UUIDs both return 404. Tags are only read through an already scoped
parent. Version predicates protect metadata updates; deletion locks the scoped document row.

V3 adds `page_count`, `vault_document_tag`, `vault_blob_cleanup` and indexes. V1/V2 are unchanged.
Tags have a normalized child table (maximum 12 input tags, 40 characters each); V1's reserved
JSON metadata/text-array columns are not accepted from clients and remain unused. No extraction
confidence is invented. Existing schema timestamps, owner FK, type/status checks and version remain.
Filename/provider substring searches use escaped SQL LIKE with capped pagination and deterministic
upload-date/UUID ordering. The owner/upload index supports the common browse path. Substring
searches can scan one owner's documents; large-scale trigram tuning awaits real PostgreSQL plans.

## File validation and storage

`DocumentStorage` exposes store/retrieve/delete/exists with opaque keys. Only
`LocalDocumentStorage` exists; an S3 adapter is future work. Root defaults to
`../.data/documents` relative to backend/, configured by STORAGE_ROOT. The root is not a web directory.
Use a private trusted volume whose parents cannot be changed by another OS account. POSIX root/file
permissions are 0700/0600 where supported; Windows relies on operator-configured ACLs.

Original filenames are NFC-normalized, length checked (255), and rejected for path separators,
control characters, traversal sequences, colon or percent encoding. Invisible format characters
are removed. A random UUID-derived 128-bit key is generated by the server; strict key validation,
CREATE_NEW and NOFOLLOW_LINKS prevent filename paths, overwrites and symlink reads/deletes.

The fixed allowlist is PDF/JPEG/PNG; it cannot be widened through an environment typo. Extension,
declared MIME, magic, actual parser/decoder and trailing markers must agree. PDFs use PDFBox 3.0.8
strict parsing: encrypted documents, active actions, embedded files/XFA, invalid pages and more
than 200 pages are rejected. Images must decode without warnings and contain no more than 20 million
pixels. PDF object traversal is iterative/bounded; decoded streams are capped at 50 MiB cumulatively,
embedded image pixels at 20 million, and page dimensions at 3000 points. Two concurrent parser/render
operations are permitted per process; excess demand returns 429. This is **not antivirus scanning or
sandboxed parser execution**; hostile-parser CPU/memory behavior still needs isolation before public deployment.

Next’s production proxy envelope is explicitly 21 MiB with a 120-second timeout, matching the
backend envelope rather than the framework’s smaller default. An actual >10 MiB upload is tested.

VAULT_MAX_BYTES is configurable from 1 byte to 20 MiB (existing database ceiling), defaults to
20971520. Servlet request cap is 21 MiB including multipart overhead. The service independently
counts bytes. Files are bounded in memory; this implementation is for a modest local workload,
not unlimited storage or tenant quotas. Client checks are feedback only.

SHA-256 is computed on the unchanged original. `verifyIntegrity` compares size and digest before
any download/preview bytes leave the service. Mismatch returns safe 409 and a content-free audit
event. Missing/unreadable bytes return 503 and the same security event. No paths or filenames are logged.

## Preview and download

The frontend authenticates every request with an in-memory access JWT. Refresh remains an HttpOnly
cookie handled by the existing client. Browser object URLs are local, temporary and revoked; no
public storage URLs or access tokens in query strings/localStorage are introduced.

PDF preview renders one page to PNG using PDFBox (no text extraction). The browser receives pixels,
not PDF JavaScript, links or attachments. Images preview as their verified original image type.
Preview is page-based with previous/next controls. Original download always uses attachment
Content-Disposition with framework UTF-8 filename encoding. Responses have explicit MIME/length,
no-store, nosniff, CSP and frame/referrer protections. A download already returned to a user cannot
be recalled; backups/downloaded copies are outside the local deletion boundary.

## Database/file consistency

Uploads first commit a cleanup intent with a one-hour grace period, before writing any bytes. The
next transaction locks this intent, writes with CREATE_NEW, inserts metadata/tags/audit and removes
the intent atomically in the database. A rollback/crash leaves the cleanup intent, so an orphan is
recoverable. Ordinary failures attempt immediate cleanup. The grace period avoids racing startup;
the row lock serializes a worker with an active write. No successful metadata row is committed
before its file write completes. Power-loss durability still depends on filesystem/volume guarantees;
integrity checks fail closed if the file disappears or changes.

Deletion atomically inserts an independent cleanup row, deletes owned metadata/tags and writes
DOCUMENT_DELETED. It then attempts storage deletion. 204 means the original was removed; 202 means
metadata is inaccessible and physical deletion remains queued. The UI explains this distinction.
A scheduled worker retries up to 100 due keys every 60 seconds and survives restarts through persisted
rows. File deletion is idempotent; a database failure after file removal is safe to retry. Workers
lock queue rows and refuse to remove a key referenced by a live document. No arbitrary paths are
accepted. Repeated deletion returns the same generic 404 as any absent record.

Future dependent Visit Packs/shares are unimplemented. Existing restrictive FKs fail the transaction
safely; before enabling those modules, add explicit revocation/derived-content deletion policy.
Concurrent downloads may finish with already verified bytes or fail with 404/503 if deletion wins;
partial or unverified data is never deliberately streamed. Metadata deletion does not erase the
minimal audit event. Queue backlog metrics/backoff/retention and backup purge policy remain operational work.

## Verification boundaries

See PROJECT_STATUS.md for executed counts/commands. API tests use the real application/security,
H2 JDBC and a real temporary filesystem, with only the auth rate store/clock substituted. Native
PostgreSQL/Flyway and Redis runtime verification remain pending. Browser automation remains pending;
the production Next HTTP proxy test is not a rendered-browser test.

PDFBox stream caches additionally use a 50 MiB bounded in-memory ScratchFile; decoded-size checks
do not imply a hard limit on all parser/renderer allocations. Process isolation remains a deployment gate.
